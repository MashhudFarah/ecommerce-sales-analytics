I ran Facebook ads for two small shops for about two years, and "did the ads
actually make money?" always meant an hour in Ads Manager and a spreadsheet. So
I built this: a messy export in, sales and ad spend side by side, out.

**Sample data, generated by me — not a real shop.** The numbers below are what
this dataset produces, not results for a client.

## What it does

Two versions from the same cleaned file:

- **`dashboard.xlsx`** — five pivot charts and four slicers on a dark background
- **`streamlit run app.py`** — the same figures with sidebar filters, running locally

## Cleaning

Payment methods and countries come in with different cases and spacing —
`Net Banking` / `NetBanking` / `net banking`, `USA` / `U.S.A` / `United States`.
I normalise both.

The bigger decision was order status. I split it into fulfilled and
cancelled/returned, which is why the numbers here look smaller than they could
have. Here "fulfilled" means anything that wasn't cancelled or returned, so
shipped and pending orders count.

## What went wrong

**Cancelled and returned orders were counted as revenue.** On this data that
overstates revenue by about 22% ($1.40M instead of $1.15M), and nothing looks
broken when it happens. Fixed by splitting order status before any sum.

**A missing price silently became 0.** Pandas filled the gap and average order
value dropped for no visible reason. Now I check for nulls first.

**The ad-spend file didn't line up with the orders.** The orders run past the
end of the ad-spend file, so some ROAS values came out wrong. Fixed by joining
on date and category and trimming the order dates to the period the ad-spend
file covers.

## Limits

- The Streamlit app isn't deployed, it runs locally only
- Basic KPIs: revenue, spend, ROAS, AOV, order count. No forecasting or cohorts
  (those are in the SQL companion)
- Sample data, so the absolute figures mean nothing. The method is the point
- The pivot charts and slicers in `dashboard.xlsx` were built by hand in Excel.
  `build_dashboard.py` writes the data, KPI and chart-data sheets to
  `dashboard_data_source.xlsx`, but it doesn't rebuild the pivots
- ROAS on the KPI card is the average of the daily per-category ROAS. Weighted
  by spend it is 3.03x, so the average understates it slightly

## Setup

```bash
git clone https://github.com/MashhudFarah/ecommerce-sales-analytics.git
cd ecommerce-sales-analytics
pip install -r requirements.txt

python clean_data_script.py     # messy_data.csv -> clean_data.xlsx
python build_dashboard.py       # -> dashboard_data_source.xlsx
streamlit run app.py            # local web app
```

Step 1 has to run first — step 2 reads `clean_data.xlsx`. The app reads
`dashboard.xlsx` and falls back to `clean_data.xlsx` if it isn't there.

## Definitions

- **Gross revenue** — all orders, including cancelled and returned. $1.40M
- **Fulfilled revenue** — everything except cancelled and returned, so
  delivered, shipped and pending. $1.15M
- **Lost revenue** — cancelled and returned. $253K
- **Avg ROAS** — fulfilled revenue ÷ ad spend for each day and category, then
  averaged. 2.94x
- **Revenue after ad spend** — fulfilled revenue minus ad spend, on the days
  that had ad spend. $760K. The dashboard card calls this "Profit After Ads",
  but it is **not profit** — no cost of goods, shipping or platform fees

The [SQL companion](https://github.com/MashhudFarah/ecommerce-sql-analytics)
is stricter: it counts only delivered orders as fulfilled ($767K) and divides by
total ad spend, which gives a ROAS of about 2.04x. Same data, different
definition. Pending and shipped orders can still be cancelled, so the stricter
one is the safer number, and moving the dashboard to it is the next change I'd
make.

Companion: [E-commerce SQL Analytics](https://github.com/MashhudFarah/ecommerce-sql-analytics), same dataset in SQLite.
